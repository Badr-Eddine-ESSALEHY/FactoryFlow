# 1. Database Purpose

The database exists to transform FactoryFlow from a temporary mobile utility into a trustworthy industrial information system.

It must preserve:

- user identity
- configurable KPI vocabulary
- source report context
- extracted candidate values
- final confirmed values
- report lifecycle
- generated document metadata
- schedules
- notifications
- auditability
- historical traceability

The database must reflect business reality rather than UI layout.

---

# 2. Database Technology

Approved:

```text
PostgreSQL
```

Reasons:

- strong relational integrity
- mature indexing
- transactional reliability
- excellent Spring Data JPA support
- suitable for audit/history
- appropriate for reporting queries
- scalable far beyond current user count

---

# 3. Persistence Principles

FactoryFlow database design follows:

```text
Business meaning > UI convenience
Integrity > shortcuts
History > destructive simplification
Confirmed data > temporary extraction
Configuration > hardcoded parser vocabulary
```

---

# 4. Authoritative Data Rule

The backend + PostgreSQL are authoritative for:

- confirmed maintenance reports
- final KPI values
- KPI definitions
- report history
- generated report metadata
- schedules
- notification records where persisted
- audit history

Android Room is only:

```text
cache / local support / draft resilience
```

not authoritative business storage.

# 7. Primary Key Strategy

Recommended:

```text
BIGINT generated identity
```

for most business tables.

Example:

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

UUIDs are not required unless a concrete integration/distribution need appears.

---

# 8. Timestamp Strategy

Use timestamps consistently.

Recommended backend storage:

```text
TIMESTAMP WITH TIME ZONE
```

for globally meaningful event timestamps such as:

- created_at
- submitted_at
- generated_at
- occurred_at
- updated_at

Report-period dates may use:

```text
DATE
```

where time is not part of the business meaning.

# 9. User Table

Baseline:

```text
users
-----
id
name
email
password_hash
active
created_at
updated_at
```

Recommended conceptual DDL:

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(254) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_users_email UNIQUE (email)
);
```

---

# 10. User Email Rule

Email is unique.

Application logic should normalize consistently where appropriate.

Do not silently create duplicate users because of email casing differences.

A lower-case normalized storage convention is preferred.

---

# 11. User Role Rule

Do not add a role column in the initial schema.

Current product has one effective role:

```text
Maintenance Engineer
```

If roles are introduced later, add them through an explicit migration and business requirement.

---

# 12. User Deactivation

Use:

```text
active = false
```

rather than hard deleting users referenced by historical reports.

Historical authorship must remain readable.

```sql
CREATE TABLE kpi_definitions (

    code VARCHAR(100) NOT NULL,

            OR plausible_min <= plausible_max
        )

```

# 16. Alias Uniqueness

A normalized alias should not ambiguously map to multiple active KPIs.

The database can enforce global uniqueness initially.

If future requirements demand context-sensitive aliases, the model must be revisited deliberately.

---

# 17. KPI Deactivation

Use:

```text
active = false
```

instead of deleting definitions used historically.

New parser analysis should ignore inactive KPI definitions by default.

Historical KPI entries remain linked.

---

# 18. Plausible Range

Use:

```text
NUMERIC
```

not floating point.

These values are warning thresholds, not always hard constraints.

```text

```

Do not use ordinal enum storage.

# 21. Report Status Enum

Recommended conceptual lifecycle:

```text
DRAFT
PENDING_REVIEW
CONFIRMED
```

`ARCHIVED` is excluded unless a later approved implementation genuinely requires it.
Missing/generated/combined dashboard indicators are read-model projections, not
persisted report states. Multiple reports may share the same `effective_date`.

Generated-document status must not be mixed into this enum.

`GENERATED` belongs to generated-document state, not necessarily MaintenanceReport state.

---

# 22. Raw Text

`raw_text` may be null for purely manual entry if no source text exists.

For paste/OCR it should preserve the actual source text used for analysis.

---

# 23. Source Image Storage

Original images are not required in the current database model.

Do not add image BLOB columns.

If future image archival is required, store file/object references rather than large binary data in core tables where possible.

# 25. KPI Entry DDL

Conceptual:

```sql
CREATE TABLE kpi_entries (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    report_id BIGINT NOT NULL,
    kpi_definition_id BIGINT NOT NULL,
    source_label VARCHAR(255),
    source_line TEXT,
    extracted_value NUMERIC(20,6),
    current_value NUMERIC(20,6),
    final_value NUMERIC(20,6),
    confidence_score NUMERIC(5,4),
    edited_by_user BOOLEAN NOT NULL DEFAULT FALSE,
    captured_unit VARCHAR(50),
    warning_codes TEXT[] NOT NULL DEFAULT '{}',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT fk_kpi_entry_report
        FOREIGN KEY (report_id)
        REFERENCES maintenance_reports(id)
        ON DELETE CASCADE,
    CONSTRAINT fk_kpi_entry_definition
        FOREIGN KEY (kpi_definition_id)
        REFERENCES kpi_definitions(id),
    CONSTRAINT ck_kpi_entry_confidence
        CHECK (
            confidence_score IS NULL
            OR (confidence_score >= 0 AND confidence_score <= 1)
        )
);
```

---

# 26. Extracted Value

`extracted_value` is the parser/manual candidate before final confirmation.

For manual entry it may equal the entered value or may be null if the domain chooses to distinguish manual input from extraction.

Exact semantics must be kept consistent in backend code. One source line may produce
zero, one, or multiple KPI entries/candidates.

---

# 27. Final Value

`final_value` becomes authoritative only when the report is confirmed.

Before confirmation it may:

- be null
- mirror current reviewed draft value

The final backend model should avoid ambiguity.

A canonical draft field is:

```text
current_value
```

separate from:

```text
final_value
```

for server-side drafts.

Do not add a separate persisted per-KPI `PENDING`, `VALIDATED`, `REJECTED`, or
`CORRECTED` state machine for MVP.

---

# 28. Edited By User

`edited_by_user` tracks whether the user modified the candidate.

It supports:

- auditability
- parser quality evaluation
- future parser improvement

---

# 29. Duplicate KPI Constraint

Do not automatically enforce:

```text
UNIQUE(report_id, kpi_definition_id)
```

until duplicate source handling is finalized.

Why:

A duplicate KPI may need to be represented temporarily during analysis.

Recommended approach:

- analysis candidates may exist outside authoritative `kpi_entries`
- confirmed entries should likely become unique per report + KPI definition

If authoritative confirmed table semantics are one KPI per report, enforce uniqueness after the final workflow is fixed.

---

# 30. Analysis Candidate Persistence

Preferred design:

Parser analysis results do **not** need to be persisted as authoritative `kpi_entries` immediately.

Options:

### Option A — Transient analysis

Analyze endpoint returns extraction DTOs.

Only draft/confirm persists.

### Option B — Draft persistence

Persist draft report + candidate entries.

Both are acceptable.

The final choice belongs in backend/API implementation.

Do not persist temporary analysis in a way that pollutes official queries.

---

# 31. Unrecognized Line Storage

Unrecognized content is persisted for drafts and confirmed traceability in:

```text
report_unrecognized_lines
```

Conceptual:

```text
id
report_id
source_line
resolution_status
resolved_kpi_definition_id
```

Canonical `resolution_status` values are `UNRESOLVED`, `ASSIGNED`, and `IGNORED`.

Do not overload `kpi_entries` with fake KPI IDs.

---

# 32. Report Unrecognized Lines Table

Required for persisted drafts and confirmed traceability:

```sql
CREATE TABLE report_unrecognized_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    report_id BIGINT NOT NULL,
    source_line TEXT NOT NULL,
    resolution_status VARCHAR(40) NOT NULL,
    resolved_kpi_definition_id BIGINT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT fk_unrecognized_report
        FOREIGN KEY (report_id)
        REFERENCES maintenance_reports(id)
        ON DELETE CASCADE,
    CONSTRAINT fk_unrecognized_kpi
        FOREIGN KEY (resolved_kpi_definition_id)
        REFERENCES kpi_definitions(id),
    CONSTRAINT ck_unrecognized_resolution
        CHECK (resolution_status IN ('UNRESOLVED', 'ASSIGNED', 'IGNORED'))
);
```

# 48. Schedule Timezone

Store timezone explicitly.

Example:

```text
Africa/Casablanca
```

Do not rely on server default timezone.

Weekly reporting periods are Monday through Sunday. Monthly schedules run at the
configured time on the first day of the following month and generate the complete
previous calendar month; no configurable `day_of_month` is stored for MVP.

# 56. Refresh Token Table

Opaque random refresh tokens use server-side hash persistence:

```text
refresh_tokens
--------------
id
user_id
token_hash
expires_at
revoked_at
created_at

```

Never store raw refresh tokens. Rotation sets `revoked_at` and links the replacement;
`POST /api/auth/logout` revokes the active refresh/session token.

# 64. Normalization of Business Data

Prefer normalized relational design for:

- aliases
- schedule recipients
- generated report source links

Do not normalize every tiny value into its own table.

Balance clarity and query simplicity.

---

# 65. Enum Persistence

Persist enum values as strings.

Good:

```text
CONFIRMED
GALLERY_OCR
EXCEL
```

Avoid ordinal storage:

```text
0
1
2
```

because enum order changes can corrupt meaning.

---

# 66. Numeric Precision

Recommended:

```text
NUMERIC(20,6)
```

for KPI values as a safe baseline.

Actual precision/scale may be tuned to real data.

Do not use PostgreSQL `REAL`/`DOUBLE PRECISION` for business values unless justified.

---

# 67. Confidence Precision

Recommended:

```text
NUMERIC(5,4)
```

for values between 0 and 1.

Example:

```text
0.9325
```

---

# 68. Unit Storage

Units may remain VARCHAR because they are domain labels such as:

```text
t
kg
%
m3
```

If unit conversion becomes a real feature later, a dedicated unit model may be introduced.

---

# 69. Soft Delete Strategy

Do not implement a generic `deleted_at` on every table.

Use business-specific lifecycle.

Examples:

```text
users.active
kpi_definitions.active
report_schedules.enabled
```

Historical reports are generally retained.

---

# 70. Hard Delete Strategy

Hard delete is acceptable for:

- transient draft-only child rows
- revoked/stale technical tokens
- temporary analysis artifacts

when no historical business value remains.

---

# 71. Cascade Rules

Use cascade deletion carefully.

Good candidate:

```text
maintenance_report draft deleted
→ its draft kpi_entries deleted
```

Historical confirmed reports should not be casually deleted.

---

# 72. Foreign Key Strategy

Use explicit foreign keys.

Do not rely only on JPA relationships.

The database must protect referential integrity.

---

# 73. Indexing Strategy

Create indexes based on real query patterns.

Initial candidates:

```text
users(email)
kpi_definitions(code)
kpi_aliases(normalized_alias)
maintenance_reports(submitted_at)
maintenance_reports(effective_date)
maintenance_reports(status)
maintenance_reports(submitted_by)
kpi_entries(report_id)
kpi_entries(kpi_definition_id)
generated_reports(generated_at)
generated_reports(type)
generated_reports(generation_status)
notifications(user_id, created_at)
report_schedules(enabled)
schedule_runs(schedule_id, scheduled_for)
```

---

# 74. Composite Indexes

Potential:

```text
maintenance_reports(status, effective_date DESC, submitted_at DESC)
generated_reports(type, generated_at DESC)
notifications(user_id, read_at, created_at DESC)
```

Add only after observing query patterns.

---

# 75. Search Indexing

If search by KPI/report grows:

Use PostgreSQL indexes/projections appropriate to the final query design.

Do not add Elasticsearch for this project.

---

# 76. Dashboard Query Strategy

Dashboard should not load every report and calculate in Java.

Prefer focused queries/projections for:

- latest KPI values
- today's status
- recent reports
- pending drafts
- upcoming schedule

---

# 77. Statistics Query Strategy

Use PostgreSQL aggregation where appropriate:

```sql
AVG
MIN
MAX
GROUP BY
DATE_TRUNC
```

Return only the data Android needs.

---

# 78. Historical Latest KPI Query

A common need:

```text
latest confirmed value per KPI
```

This should be implemented efficiently through query/projection rather than scanning all entries in application memory.

---

# 79. Report History Pagination

Use pagination.

Do not return unlimited report history.

---

# 80. Generated Report History Pagination

Likewise paginate if data grows.

---

# 81. N+1 Protection

Watch relationships such as:

```text
reports → entries → definitions
```

Do not generate dozens of extra queries per report list.

Use:

- projections
- fetch joins
- entity graphs

where appropriate.

---

# 82. Fetch Type

Do not make every relationship EAGER.

Default toward lazy/explicit loading where safe.

---

# 83. JPA Relationship Guidance

Potential:

```text
User 1 → * MaintenanceReport
MaintenanceReport 1 → * KPIEntry
KPIDefinition 1 → * KPIEntry
```

Bidirectional collections should be added only when useful.

---

# 84. Orphan Removal

Use only when child lifecycle is truly owned by parent.

Example:

A draft report's temporary entries may be composition-like.

Historical references to KPI definitions are not.

---

# 85. Optimistic Locking

Consider:

```java
@Version
```

for mutable records such as drafts/schedules.

This helps detect silent concurrent overwrites.

Potential tables:

```text
maintenance_reports
report_schedules
```

Do not add optimistic locking everywhere automatically.

---

# 86. Confirmed Report State Protection

Backend update queries/services must reject modification of confirmed report business values unless an explicit correction workflow exists.

Database constraints alone may not fully express this.

Application service enforces it.

---

# 87. Transaction Boundaries

Typical transactional operation:

```text
confirm report
```

may persist:

- report status
- final KPI entries
- confirmed timestamp
- audit records

as one coherent transaction.

---

# 88. Report Generation Transaction Boundary

Do not hold one DB transaction open throughout slow file generation/email.

Preferred:

```text
read authoritative data
→ generate file
→ persist generated report result in short transaction
→ send email separately
```

Exact orchestration may vary.

---

# 89. Schedule Run Transaction Boundary

Quartz execution should update run status reliably.

Avoid long database locks around external SMTP/file operations.

---

# 90. Data Integrity Constraints

At minimum consider:

```text
unique user email
unique KPI code
valid plausible range
confidence between 0 and 1
period_start <= period_end
valid calendar-period semantics
foreign keys
non-null required status/source
```

---

# 91. Business Constraints Not Suitable for SQL Alone

Examples:

- confirmation required before official statistics
- warning vs rejection
- parser fuzzy matching
- report state transition rules
- scheduled period selection

These remain in application/domain logic.

---

# 92. State Transition Rules

Recommended MaintenanceReport transition:

```text
DRAFT
→ PENDING_REVIEW
→ CONFIRMED
```

Possible:

```text
DRAFT
→ CONFIRMED
```

for manual workflows if the review screen is still completed.

Do not allow:

```text
CONFIRMED
→ DRAFT
```

without an explicit correction workflow.

---

# 93. Generated Report Transition

If async states exist:

```text
PENDING
→ GENERATING
→ READY
```

or:

```text
PENDING
→ GENERATING
→ FAILED
```

---

# 94. Schedule Run Transition

```text
STARTED
→ SUCCEEDED
```

or:

```text
STARTED
→ PARTIAL_SUCCESS
```

or:

```text
STARTED
→ FAILED
```

---

# 95. Notification Transition

```text
UNREAD
→ READ
```

If modeled via `read_at`:

```text
NULL
→ timestamp
```

---

# 96. Refresh Token Transition

```text
ACTIVE
→ REVOKED / EXPIRED / ROTATED
```

represented by timestamps/relationships rather than necessarily one enum.

---

# 97. Database Migration Strategy

Flyway files live in:

```text
backend/src/main/resources/db/migration
```

Recommended naming:

```text
V1__create_users.sql
V2__create_kpi_catalog.sql
V3__create_maintenance_reports.sql
V4__create_generated_reports.sql
...
```

or one coherent initial schema migration if preferred.

---

# 98. Migration Granularity

A migration should represent one coherent schema change.

Do not create 50 tiny migrations before the first working schema.

Do not create one giant forever migration after development begins.

---

# 99. Applied Migration Rule

Never edit an already-applied migration in a shared environment.

Create a new migration.

---

# 100. Seed Data Strategy

Development seed data may include:

- demo maintenance engineer
- anonymized KPI definitions
- parser aliases
- demo reports

Do not seed private production credentials.

---

# 101. Flyway Seed Data

Separate structural migrations from environment-specific demo data where practical.

Potential:

```text
V1__schema.sql
V2__initial_kpi_catalog.sql
```

Do not put private company data into public migrations.

---

# 102. Demo User

If a demo user is seeded:

Use a clearly non-production credential.

Document it only in safe development instructions.

---

# 103. Real WhatsApp Data

Do not store private real screenshots/messages in database seeds.

Use anonymized equivalents.

The original top-level `assets/` screenshots are private context and must remain
unchanged. Never use them directly in seeds, tests, the academic report, GitHub, or
portfolio/demo material; use sanitized derivatives created later.

---

# 104. Database Test Strategy

Test:

- migration from clean DB
- unique constraints
- relationships
- query correctness
- report confirmation persistence
- latest KPI queries
- report history filters
- generated report metadata
- schedule persistence

---

# 105. PostgreSQL-Specific Testing

When relying on PostgreSQL behavior:

Prefer testing against PostgreSQL-compatible environment.

Do not assume H2 reproduces all PostgreSQL semantics.

---

# 106. Clean Database Test

The project must be able to:

```text
create empty PostgreSQL database
→ run application/Flyway
→ obtain valid schema
```

This is a release-readiness requirement.

---

# 107. Backup Philosophy

Formal production backup is outside the initial sprint.

However, the schema must be designed in a way that normal PostgreSQL backup/restore mechanisms can protect business data.

Do not store critical business state only in generated files.

---

# 108. Data Retention

No automatic retention/deletion policy is defined initially.

Therefore:

- confirmed reports retained
- KPI entries retained
- generated metadata retained
- audit logs retained

until a future explicit policy exists.

---

# 109. Generated File Retention

Generated file storage may require future cleanup policy.

Do not delete files automatically without corresponding metadata policy.

---

# 110. Timezone Rule

Application/server/database must use explicit timezone semantics.

Moroccan deployments should not depend blindly on server default timezone because DST/timezone rules may change.

Use IANA timezone identifiers.

---

# 111. Audit Timezone

Store globally meaningful audit timestamps with timezone.

Display localized on Android.

---

# 112. Report Period Storage

Use:

```text
DATE
```

for `period_start` and `period_end`.

This avoids timezone ambiguity for calendar reporting periods.

---

# 113. Schedule Time Storage

Use local schedule time + explicit timezone.

Do not convert business schedule to arbitrary server-local time without preserving zone.

---

# 114. JSONB Policy

Use JSONB only for:

- audit metadata
- flexible optional configuration

Do not store core report/KPI structures as JSON blobs.

The relational model is intentional.

---

# 115. No EAV Model

Do not create a generic entity-attribute-value system.

KPI entries already provide a flexible relational structure.

---

# 116. No One-Column-Per-KPI Model

Do not design:

```text
maintenance_reports
  choline
  vrac
  kpi_x
  kpi_y
```

because KPI vocabulary is configurable and reports can be partial.

Use:

```text
maintenance_reports
+
kpi_entries
```

---

# 117. No Spreadsheet-Shaped Database

The database should not mimic Excel cells.

It should model business concepts.

---

# 118. No Binary Excel/PDF in Core Tables

Store files externally through storage abstraction.

Persist metadata/path.

---

# 119. No Database Logic in Android

Android never connects directly to PostgreSQL.

---

# 120. No Business Logic in Triggers

Avoid PostgreSQL triggers for core workflow unless a concrete need appears.

Keep business behavior in Spring services where it is testable and visible.

---

# 121. Database Views

Views may be introduced for reporting/read-model simplification if useful.

Do not add them before a real query need.

---

# 122. Materialized Views

Not required initially.

Statistics volume is small.

---

# 123. Partitioning

Not required.

Initial data scale does not justify it.

---

# 124. Sharding

Not required.

---

# 125. Read Replicas

Not required.

---

# 126. Cache Layer

No Redis requirement.

Do not introduce cache infrastructure without measured need.

---

# 127. Search Engine

No Elasticsearch/OpenSearch requirement.

PostgreSQL search/filtering is sufficient for current scope.

---

# 128. Schema Documentation Standard

Every table in the final implementation should document:

- purpose
- key columns
- relationships
- lifecycle
- indexing rationale

This document should evolve as migrations are added.

---

# 130. Core Report Provenance

A generated report should be traceable to the confirmed maintenance data used to create it.

This is especially valuable for:

- weekly reports
- monthly reports
- audits
- debugging

Use `generated_report_sources` if required by implementation.

---

# 131. Historical KPI Rename

If `display_name` changes later:

Historical `kpi_entries` still point to the same KPI definition.

If preserving the exact historical display label becomes necessary, add snapshot fields deliberately.

Do not duplicate everything prematurely.

---

# 132. Historical Unit Change

If a KPI's expected unit changes:

Historical entries may need their captured unit preserved.

This is why `captured_unit` is useful.

---

# 133. Historical Plausibility Range Change

Changing current plausible range must not rewrite old confirmed values.

Warnings are evaluated at analysis time.

If historical warning reproducibility is important, preserve warning code/context on the entry.

---

# 134. Parser Confidence History

Persisting confidence on entries supports:

- parser quality analysis
- explanation of past corrections
- future improvement

It does not make confidence official business data.

---

# 135. User Correction Analysis

Future parser quality analysis may query:

```text
edited_by_user = true
```

to identify labels/rules frequently corrected by engineers.

This is valuable without using AI in official extraction.

---

# 136. Report Completion Metrics

Future statistics may include:

- number of confirmed reports
- draft count
- missing expected reports
- generated report count

These should be derived from business records, not duplicate summary counters unless performance requires.

---

# 137. Notification Cleanup

If notification volume grows, a retention policy may be added.

No automatic cleanup initially.

---

# 138. Device Token Cleanup

Invalid FCM tokens should be deactivated/removed.

This is technical housekeeping and does not affect business history.

---

# 139. Refresh Token Cleanup

Expired/revoked refresh tokens may be periodically cleaned if the table grows.

This is technical data, not business history.

---

# 140. Audit Log Deletion

Do not casually delete audit history.

If retention is ever required, define it explicitly.

---

# 141. Data Privacy

Before public presentation:

Ensure development DB dumps do not contain:

- real private phone numbers
- confidential names
- real SMTP credentials
- real access tokens
- sensitive industrial values

---

# 142. Database Dumps

Do not commit database dumps to Git unless intentionally anonymized and required.

---

# 143. `.env` / Secrets

Database credentials belong outside Git.

Provide example config without real secrets.

---

# 144. Migration Rollback

Flyway community workflows normally favor forward migrations.

Do not rely on manual rollback scripts unless project workflow deliberately introduces them.

Fix schema mistakes with new migrations.

---

# 145. Production-Safe Migration Mindset

Even during portfolio development, avoid migrations that casually destroy historical data.

Prefer:

```text
add
migrate
verify
remove later
```

over immediate destructive changes.

---

# 146. Schema Review Checklist

Before accepting a migration:

```text
[ ] Does it model a real business need?
[ ] Is naming consistent?
[ ] Are foreign keys correct?
[ ] Are nullability rules correct?
[ ] Are enum strings stable?
[ ] Is historical integrity preserved?
[ ] Are indexes justified?
[ ] Are numeric types appropriate?
[ ] Are timestamps/timezones correct?
[ ] Can a clean DB apply all migrations?
[ ] Does documentation need update?
```

---

# 147. Query Review Checklist

Before accepting a repository query:

```text
[ ] Does it return only needed data?
[ ] Does it accidentally load huge graphs?
[ ] Is pagination required?
[ ] Is an index useful?
[ ] Is there an N+1 risk?
[ ] Does it use confirmed data where required?
[ ] Does it preserve active/inactive semantics?
```

---

# 148. Confirmation Persistence Checklist

```text
[ ] report exists
[ ] report not already confirmed
[ ] authenticated user allowed
[ ] effective_date present and distinct from event timestamps
[ ] KPI definitions valid
[ ] final values valid
[ ] extracted values preserved
[ ] edited flags correct
[ ] unknown lines persisted with explicit resolution
[ ] confirmed_at set
[ ] transaction atomic
[ ] audit written if enabled
```

---

# 149. Generated Report Persistence Checklist

```text
[ ] reporting period correct
[ ] source data confirmed
[ ] format correct
[ ] file generation succeeded
[ ] storage reference valid
[ ] metadata persisted
[ ] origin stored
[ ] generation status correct

[ ] regeneration creates a new version with provenance
```

# 150. Schedule Persistence Checklist

```text
[ ] type valid
[ ] time valid
```

# 151. Notification Persistence Checklist


# 152. Database Definition of Done

Database work is complete only when:

```text
[ ] migration exists
[ ] migration applies cleanly
[ ] JPA model matches schema
[ ] repository behavior tested
[ ] constraints tested
[ ] relevant API still works
[ ] no destructive accidental data loss
[ ] docs updated
```

# 153. Database Roadmap

Recommended implementation sequence:

```text
1. users
2. refresh_tokens
3. kpi_definitions
4. kpi_aliases
5. maintenance_reports
6. kpi_entries
7. unrecognized lines if persisted
8. generated_reports
9. generated_report_sources if needed
10. report_schedules
11. schedule recipients
12. schedule runs
13. notifications
14. device_tokens
15. audit_log
```

Do not create later tables before their features are scheduled.

---

# 154. Final Database Principle

The database must make it possible to answer:

```text
What was reported?
Where did it come from?
What did the parser extract?
What did the engineer finally confirm?
Who confirmed it?
When?
Which generated documents used it?
What happened afterward?
```

If the schema cannot preserve those answers, it is not complete enough for FactoryFlow.
