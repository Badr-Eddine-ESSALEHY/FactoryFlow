# 1. API Philosophy

FactoryFlow uses REST as the primary authoritative client/server contract.

The API should be:

- predictable
- resource-oriented
- explicit
- easy to consume from Retrofit
- easy to document in OpenAPI
- stable enough for Android development
- clear about errors
- clear about authoritative vs non-authoritative operations

Realtime WebSocket/STOMP complements REST.

It does not replace REST.

---

# 2. Base Path

Initial base path:

```text
/api
```

Examples:

```text
/api/auth/login
/api/reports
/api/kpi-definitions
```

Explicit `/v1` versioning is not required in the first implementation.

If a future breaking compatibility requirement appears, introduce versioning deliberately.

Do not mix:

```text
/api/...
```

and:

```text
/api/v1/...
```

inside the same implementation.

---

# 3. Content Type

Primary request/response type:

```text
application/json
```

File endpoints use appropriate MIME types.

Examples:

```text
application/pdf
application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
```

---

# 4. Authentication

Protected endpoints use:

```http
Authorization: Bearer <access_token>
```

The access token is a JWT.

Refresh token handling is described below.

---

# 5. Public Endpoints

Only explicitly approved endpoints should be public.

Core public endpoints:

```text
POST /api/auth/login
POST /api/auth/refresh
```

Potential development/documentation endpoints:

```text
Swagger/OpenAPI
health
```

according to Spring Security configuration.

All business data endpoints require authentication.

---

# 6. Standard Date/Time Formats

Use ISO 8601.

Examples:

```text
2026-08-11
2026-08-11T14:20:00Z
2026-08-11T15:20:00+01:00
```

Android should parse timestamps, then localize presentation.

---

# 7. Numeric Representation

KPI numeric values are JSON numbers where practical.

Example:

```json
{
  "value": 15.8
}
```

The backend must use decimal-safe Java types such as `BigDecimal`.

Do not expose binary floating-point artifacts.

---

# 8. Enum Representation

Enums are strings.

Good:

```json
{
  "source": "PASTE",
  "status": "CONFIRMED"
}
```

Avoid ordinal values.

---

# 9. Standard Error Response

All API errors should use one consistent envelope.

Recommended:

```json
{
  "timestamp": "2026-08-11T14:20:00Z",
  "status": 400,
  "code": "REPORT_VALIDATION_FAILED",
  "message": "The report contains invalid confirmation data.",
  "path": "/api/reports/42/confirm",
  "details": [
    {
      "field": "entries[1].finalValue",
      "message": "A final value is required."
    }
  ]
}
```

---

# 10. Error Field Semantics

## `timestamp`

Server timestamp.

## `status`

HTTP status.

## `code`

Stable machine-readable FactoryFlow code.

## `message`

Human-readable API message suitable for mapping to UI.

## `path`

Request path.

## `details`

Optional structured validation details.

# 13. Pagination Convention

List endpoints that can grow should use:

```text
page
size
sort
```

Example:

```text
GET /api/reports?page=0&size=20&sort=submittedAt,desc
```

Page indexing:

```text
0-based
```

---

# 14. Pagination Response

Recommended:

```json
{
  "content": [],
  "page": 0,
  "size": 20,
  "totalElements": 0,
  "totalPages": 0,
  "first": true,
  "last": true
}
```

Do not expose Spring `Page` implementation details accidentally if they make the contract unstable.

Use a dedicated page DTO if needed.

# 16. POST `/api/auth/login`

Authenticates a maintenance engineer.

## Request

```json
{
  "email": "engineer@example.com",
  "password": "example-password"
}
```

## Validation

```text
email required
email syntactically valid
password required
```

## Success

```text
200 OK
```

```json
{
  "accessToken": "<jwt>",
  "refreshToken": "<refresh-token>",
  "tokenType": "Bearer",
  "expiresInSeconds": 900,
  "user": {
    "id": 1,
    "name": "Demo Engineer",
    "email": "engineer@example.com"
  }
}
```

## Errors

```text
400 VALIDATION_ERROR
401 AUTH_INVALID_CREDENTIALS
403 AUTH_USER_INACTIVE
```

Do not distinguish unknown email from wrong password in the user-facing authentication error.

---

# 17. POST `/api/auth/refresh`

Obtains a new access token.

## Request

```json
{
  "refreshToken": "<refresh-token>"
}
```

## Success

```text
200 OK
```

```json
{
  "accessToken": "<new-jwt>",
  "refreshToken": "<rotated-refresh-token>",
  "tokenType": "Bearer",
  "expiresInSeconds": 900
}
```

Refresh tokens are opaque random values. The server stores only their hashes with
expiration/revocation metadata and rotates the token on every successful refresh.

## Errors

```text
401 AUTH_REFRESH_INVALID
401 AUTH_TOKEN_EXPIRED
```

---

# 18. POST `/api/auth/logout`

Revokes the active refresh/session token.

## Request

```json
{
  "refreshToken": "<refresh-token>"
}
```

## Success

```text
204 No Content
```

The backend marks the stored token hash revoked. Android also clears local session material.

# 28. Analyze Response Rules

The response must preserve enough information for human review.

It should expose:

```text
matched KPI
source line
candidate value
unit
confidence
warnings
unrecognized lines
```

Do not return only:

```text
{ "VRAC": 15.8 }
```

because that destroys explainability.

One source line may yield zero, one, or multiple entry candidates. Candidate IDs are
response-local correlation values only. Multi-measurement lines must not be collapsed
into one composite numeric value.

---

# 29. Analyze Warnings

Potential warning codes:

```text
LOW_CONFIDENCE
OUTSIDE_PLAUSIBLE_RANGE
MISSING_VALUE
DUPLICATE_KPI
UNIT_MISMATCH
AMBIGUOUS_NUMBER
```

Example:

```json
{
  "code": "OUTSIDE_PLAUSIBLE_RANGE",
  "message": "The value is outside the expected range.",
  "severity": "WARNING"
}
```

# 30. Unrecognized Line Example

# 38. POST `/api/reports/{id}/confirm`

Confirms an existing server-side draft. This is the only production confirmation route.
The global `POST /api/reports/confirm` contract does not exist.

Request:

```json
{
  "entries": [
    {
      "kpiDefinitionId": 12,
      "finalValue": 16.1
    }
  ],
  "unrecognizedLineResolutions": [
    {
      "lineId": 7,
      "resolution": "IGNORED"
    }
  ]
}
```

The backend preserves extracted/current values and writes final confirmed values
transactionally. Confirmation requires every unknown line to be `ASSIGNED` or `IGNORED`.

# 53. Generated Report API

# 54. POST `/api/generated-reports`

Canonical period-based generation endpoint.

## Request

```json
{
  "type": "DAILY",
  "format": "PDF",
  "periodStart": "2026-08-11",
  "periodEnd": "2026-08-11"
}
```

This route is preferable for period-based generation because weekly/monthly files may aggregate multiple maintenance reports.

## Success

For synchronous generation:

```text
201 Created
```

```json
{
  "id": 501,
  "type": "DAILY",
  "format": "PDF",
  "periodStart": "2026-08-11",
  "periodEnd": "2026-08-11",
  "origin": "MANUAL",
  "generationStatus": "READY",
  "emailDeliveryStatus": "NOT_REQUESTED",
  "version": 1,
  "generatedAt": "2026-08-11T18:00:00Z",
  "fileName": "FactoryFlow_Daily_2026-08-11.pdf"
}
```

Core generation is synchronous. Intentional regeneration creates a new
`GeneratedReport` version with provenance instead of overwriting a prior record.

For a future explicitly approved async API evolution:

```text
202 Accepted
```

with:

```text
PENDING / GENERATING
```

status.

---

# 55. Canonical Generation Rule

Daily, weekly, and monthly documents may aggregate multiple maintenance reports.
The only production generation contract is:

```text
POST /api/generated-reports
```

Do not implement competing report-specific `generate/excel`, `generate/pdf`,
`generate-excel`, or `generate-pdf` routes.

# 66. Schedule Validation

Rules:

```text
DAILY
→ no dayOfWeek required

WEEKLY
→ dayOfWeek required

MONTHLY
→ no dayOfMonth field; fixed first-day/previous-month semantics

emailEnabled=true
→ at least one valid recipient if delivery requires explicit recipients
```

Quartz may perform one recovery execution after one missed run. The backend must
deduplicate by schedule + reporting period + format.

# 84. API Contract for Missing Values

Do not serialize missing KPI values as:

```json

```

Use:

```json
null
```

or omit the value field according to the DTO contract.

Prefer explicit:

```json

  "reported": false
}
```

where the distinction benefits Android.

# 85. API Contract for Warnings

Warnings should be structured.

Recommended:

```json
{
  "code": "LOW_CONFIDENCE",
  "severity": "REVIEW",
  "message": "The KPI label was matched approximately."
}
```

Do not force Android to parse warning text.

---

# 86. API Contract for Confidence

Use numeric score:

```text
0.0–1.0
```

plus optional presentation-level category:

```text
HIGH
REVIEW
LOW
```

Backend owns score/category rules.

Android should not recalculate confidence independently.

---

# 87. API Contract for Units

Return both:

```text
capturedUnit
expectedUnit
```

where source/unit comparison matters.

Confirmed/report-detail DTO may simplify to final canonical `unit` where appropriate.

---

# 88. API Contract for User Corrections

Confirmation payload must make user edits explicit or allow backend to derive them safely.

Preferred:

```json
{
  "extractedValue": 15.8,
  "finalValue": 16.1,
  "editedByUser": true
}
```

Backend should not blindly trust `editedByUser` if it can compare values itself.

---

# 89. API Contract for Ignored Unknown Lines

If unknown lines are persisted:

Confirmation may include:

```json

    77
  ]
}
```

Ignoring must be explicit.

---

# 90. API Contract for Resolved Unknown Lines

If user assigns an unknown line to a KPI:

Request may include:

```json
{
  "lineId": 77,
  "kpiDefinitionId": 12,
  "finalValue": 15.8
}
```

Do not silently turn this into a permanent alias.

# 91. Concurrency / Conflict Responses

Use:

```text
409 Conflict
```

for state conflicts.

- already confirmed

# 92. Optimistic Lock Contract

If backend uses versioning:

DTO may include:

```json
{
  "version": 3
}
```

Update requests send current version.

Stale update:

```text
409 CONFLICT
```

Do not add this field until optimistic locking is actually implemented.

---

# 113. No Entity Exposure

Never serialize JPA entities directly as the public contract.

Reasons:

- lazy-loading issues
- circular references
- persistence leakage
- unstable API
- accidental secret/internal-field exposure

Use DTOs.

---

# 114. No Generic Success Envelope Requirement

Do not wrap every success response in:

```json
{
  "success": true,
  "data": ...
}
```

unless there is a clear product need.

HTTP status already communicates success.

Use simple typed DTOs.

---

# 115. No Generic `/action` Endpoints

Avoid:

```text
POST /api/doSomething
POST /api/processData
POST /api/getReports
```

Use resource-oriented routes.

---

# 116. No Raw Exception Responses

Never return:

```text
NullPointerException
DataIntegrityViolationException
```

to Android.

Map to stable API errors.

---

# 117. No Raw Database IDs Without Context in UI

API may use numeric IDs.

Android should combine them with display names/statuses.

Users should not be expected to interpret:

```text
Report #42
```

as the primary business label unless useful.

---

# 118. API Performance Guidance

List endpoints should avoid:

- full nested entry graphs
- raw source text
- huge audit blobs
- generated file bytes

unless specifically requested.

Use detail endpoints for detail.

---

# 119. Dashboard Performance Guidance

Prefer one optimized dashboard endpoint over many sequential requests if this improves startup and remains maintainable.

Do not create one giant "everything" API for the whole app.

---

# 120. Statistics Performance Guidance

Aggregate in PostgreSQL/backend.

Do not send all historical KPI rows to Android for local aggregation.

---

# 121. Parser Performance Guidance

Analyze endpoint should remain synchronous initially if performance is acceptable.

If analysis becomes slow in practice, measure before introducing async complexity.

---

# 122. Generated Report Async Upgrade

If RabbitMQ is implemented later:

`POST /api/generated-reports` may move from:

```text
201 READY
```

to:

```text
202 PENDING
```

Android must then observe status through:

- polling
- WebSocket event
- notification

This is a deliberate contract evolution.

---

# 123. Scheduled Generation API Boundary

Quartz does not require a public endpoint to "run" production schedules.

A development/admin test trigger may exist only if explicitly needed and secured.

Do not expose dangerous scheduler controls casually.

---

# 124. Timezone Contract

Schedule DTOs should use:

```text
timezone: "Africa/Casablanca"
```

using an IANA zone identifier.

Do not rely only on numeric UTC offset.

---

# 125. Report Period Contract

Use:

```text
periodStart
periodEnd
```

as explicit dates for generated reports.

This avoids ambiguity.

---

# 126. Report Type vs Period

`type=DAILY` describes report semantics.

`periodStart/periodEnd` identifies exact source period.

Both are useful.

---

# 127. Email Delivery Status Contract

Core `generationStatus` values are `READY` and `FAILED`. `PENDING` and `GENERATING`
exist only after an explicit future async contract change.

Generated report response may include:

```text
NOT_REQUESTED
PENDING
DELIVERED
FAILED
```

Android should display business-friendly labels.

---

# 128. Schedule Run Status Contract

Potential:

```text
STARTED
SUCCEEDED
PARTIAL_SUCCESS
FAILED
SKIPPED
```

---

# 129. Partial Success Meaning

Use only if needed.

Example:

```text
file generation succeeded
email failed
```

The generated report remains available.

---

# 130. Manual Acquisition Contract

Manual entry should not create a separate incompatible API.

Preferred flow:

```text
create/update draft with manual entries
→ confirm draft
```

This preserves one report lifecycle.

---

# 131. OCR Acquisition Contract

OCR itself is not an API endpoint.

Android performs OCR.

Backend receives resulting text through:

```text
POST /api/reports/analyze
```

For MVP, OCR from one screenshot remains one review input even if multiple WhatsApp
bubbles are visible. Analysis does not auto-create or auto-split maintenance reports;
reviewed input is persisted only through the draft API.

---

# 132. Share Intent Contract

Share Intent is Android-local behavior.

No special backend endpoint is needed.

It still uses:

```text
/analyze
```

after OCR.

---

# 133. Image OCR Contract

Gallery and shared images are submitted to the authenticated `/api/ocr/recognize` endpoint. The backend delegates only text recognition to the private PaddleOCR runtime; deterministic KPI interpretation remains in the parser.

---

# 134. Image Upload Non-Requirement

FactoryFlow does not need to upload original images to backend for the core workflow.

Do not add multipart image upload API unless a future requirement explicitly requires image archival/backend OCR.

---

# 135. API Privacy

Avoid returning:

- password hashes
- SMTP credentials
- JWT signing data
- FCM service credentials
- raw filesystem paths
- unnecessary private industrial source text in list responses

---

# 136. API Logging

Do not log full sensitive request bodies indiscriminately.

Especially:

- login credentials
- tokens
- real raw source messages
- email credentials

---

# 137. Rate Limiting

Not required initially.

If authentication abuse or deployment needs later justify it, add deliberately.

---

# 138. CORS

Android native clients do not rely on browser CORS.

Configure CORS only for Swagger/dev tooling or future browser clients as needed.

Do not open `*` unnecessarily in production-like config.


# 140. Final API Principle

The API must make the business lifecycle obvious.

A reader should be able to understand:

```text
authenticate
→ acquire/analyze
→ save draft
→ confirm
→ query history/dashboard/statistics
→ generate documents
→ schedule automation
→ receive notifications
```

without reading backend implementation details.

The API is not just a transport layer.

It is the stable contract that keeps the Android product and Spring Boot information system evolving as one coherent FactoryFlow platform.
